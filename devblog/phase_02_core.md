## 1. Цель фазы: сердце системы

Фаза 2 — это момент, когда спецификации оживают в реальном железе и сокетах. Наша цель — построить надежное, асинхронное ядро `bridge_core`, на которое смогут уверенно опираться и агент Windows, и клиент Linux:
- Высокоскоростной бинарный фрейминг сокетов поверх Raw TCP.
- Асинхронные сервер и клиент с поддержкой TLS.
- Fail-Fast Heartbeat (порог реакции <= 1.5 сек).
- Пуленепробиваемый логгер аудита в `.jsonl` с гарантированным сбросом на диск через `fsync`.
- Всеядный декодер вывода Windows, решающий вечную проблему зоопарка кодировок (BOM, CP1251, CP866, ANSI).
- Модуль безопасности: криптографическая аутентификация по общему ключу (PSK + HMAC-SHA256) и защита от атак Path Traversal.

## 2. Инженерные хроники: как мы ловили демонов рантайма

Сетевое программирование никогда не бывает скучным. На этой фазе нам пришлось распутать две крутейшие системные проблемы.

### 2.1. Детективная история: загадочный `[Errno 111]` и охота на proxychains
Мы написали асинхронный TCP-сервер и клиент, запускаем первый же интеграционный тест — и натыкаемся на сюрреалистичную ошибку:
```
ConnectionRefusedError: [Errno 111] Connection refused
```
Сервер стартует, делает `asyncio.start_server("127.0.0.1", 9732)` и честно слушает сокет. Но клиент при попытке подключиться на `127.0.0.1` падает с отказом в соединении! Порт открыт, процесс один и тот же, фаервол молчит. В чём дело?

Внимательный взгляд на заголовок терминала при запуске команд дал зацепку:
```
[proxychains] DLL init: proxychains-ng 4.17
```
**Эврика!** В рабочей среде пользователя для маршрутизации трафика был активирован утилитный перехватчик `proxychains-ng` через механизм динамической компоновки `LD_PRELOAD`. 
- `proxychains` перехватывает системный вызов `connect()` в `libc` и принудительно заворачивает сокеты в удалённый SOCKS-прокси.
- Проксификатор перехватил обращение к `127.0.0.1` и попытался отрезолвить его через удалённый прокси, где, естественно, никакого нашего моста нет!
- **Решение:** Для интеграционных тестов локального транспорта и системных сокетов loopback мы изолировали вызовы, сбросив переменную перехвата: `LD_PRELOAD=""`. Локальный трафик пошёл напрямую через ядро Linux, и сокеты полетели с околонулевыми задержками!

### 2.2. Капкан Python 3.14: вечное зависание `StreamWriter.wait_closed()`
Мы тестируем наш стек на новейшем **Python 3.14.7**. И здесь нас поджидал коварный сюрприз стандартной библиотеки:
- При быстром разрыве соединения удалённой стороной или при отмене клиентских задач вызов `await writer.wait_closed()` впадал в бесконечное ожидание.
- Сокет переходил в полузакрытое состояние TCP (`FIN-WAIT` / `CLOSE-WAIT`), внутренний транспорт `asyncio` терял событие завершения, и тесты висели «до второго пришествия».
- **Решение:** Никаких блокировок рантайма! Мы завернули все вызовы закрытия потоков в защитный таймаут:
  ```python
  try:
      await asyncio.wait_for(writer.wait_closed(), timeout=0.5)
  except (TimeoutError, Exception):
      pass  # Сокет уже освобождён операционной системой, идём дальше
  ```
Теперь цикл событий освобождается мгновенно, а сервер и клиент гасятся за доли миллисекунды без единого зависания.

### 2.3. Укрощение зоопарка кодировок Windows
Консоль Windows — исторический кошмар для разработчиков. Старые DOS-утилиты отдают текст в `CP866`, русские скрипты эпохи Windows 7 любят `CP1251`, PowerShell 7 выводит `UTF-8`, но часто лепит в начало невидимый маркер порядка байтов — UTF-8 BOM (`\xef\xbb\xbf`), а иногда и UTF-16 LE (`\xff\xfe`). Вдобавок всё это обильно посыпано цветными ANSI escape-последовательностями (`\x1b[32m...`).

Если передать такой сырой мусор человеку или ИИ-агенту (`agy_cli`), агент сойдёт с ума, пытаясь распарсить кракозябры.

Мы разработали интеллектуальный декодер [`bridge_core/codec.py`](file:///home/anhelm/Projects/Bridge_Local/src/bridge_core/codec.py):
1. **Авто-срез BOM:** на лету вырезает как 3 байта UTF-8 BOM, так и 2 байта UTF-16 LE BOM.
2. **Каскадная эвристика декодирования:**
   `preferred_encoding` (если задана) → `utf-8` → `cp1251` → `cp866` → `utf-8 (replace)`.
3. **Нормализация строк:** Windows `\r\n` превращается в канонический Unix `\n`.
4. **Стриппинг ANSI:** регулярное выражение начисто вырезает все escape-коды форматирования, возвращая кристально чистый текст для парсинга и логирования.

## 3. Реализованная архитектура ядра

### 3.1. Двоичный фрейминг сокетов (`protocol.py`)
- `encode_frame(payload)`: упаковывает JSON-RPC в бинарный пакет `[0x42 0x52][uint32 length][UTF-8 bytes]` с валидацией лимита в 64 МБ.
- `read_frame(reader)`: потоково читает заголовок из `asyncio.StreamReader`, проверяет MAGIC и дочитывает точное тело фрейма без фрагментации данных.
- `write_frame(writer, payload)`: атомарно отправляет кадр и вызывает `drain()`.

### 3.2. Асинхронный транспорт с поддержкой TLS (`transport.py`)
- **`AsyncTransportServer`:**
  - Принимает соединения клиентов на базе `asyncio.start_server`.
  - Регистрирует обработчики через `register_handler(method, func)`.
  - Обеспечивает строгую маршрутизацию JSON-RPC, автоматически отдавая стандартизированные ошибки при неверном методе или сбое парсинга.
  - Поддерживает безопасное завершение соединений с отслеживанием всех активных клиентских задач.
- **`AsyncTransportClient`:**
  - Подключается с настраиваемым таймаутом через `asyncio.open_connection`.
  - Метод `call_rpc(request, timeout_sec)` сопоставляет идентификаторы запросов и ответов (`request.id == response.id`) и генерирует типизированные исключения `RpcCallError` при серверных сбоях.

### 3.3. Мгновенный Fail-Fast Heartbeat (`heartbeat.py`)
- Никаких долгих 30-секундных «зависаний», когда команда уже отправлена, а компьютер адресата уснул или выключен.
- Метод `probe(timeout_sec <= 1.5)` делает молниеносный пинг перед отправкой любых тяжелых команд или файлов.
- Фоновый мониторинг отслеживает RTT (Round-Trip Time) в миллисекундах и собирает телеметрию (нагрузка на CPU, свободная память, время аптайма узла).
- Пропуск 2 проверок автоматически переводит статус соединения в `UNREACHABLE`.

### 3.4. Атомарный аудит-логгер (`logger.py`)
- Модель безопасности требует, чтобы ни одна команда или переданный файл не пропали из истории аудита.
- Наш `AtomicJsonlLogger` пишет события в однострочный `.jsonl` формат.
- Поддерживает одновременную запись из потоков (`threading.Lock`) и асинхронных корутин (`asyncio.Lock`).
- **Защита от потери данных при краше системы:** каждый сброс буфера сопровождается системным вызовом `os.fsync(fileno)`. Данные сбрасываются из кэша ОС прямо на физический накопитель.
- Автоматическая ротация логов по датам (`pocket/logs/YYYY-MM-DD.jsonl`).
- Зарегистрирован кастомный уровень трассировки `TRACE` (уровень 5, более детальный, чем `DEBUG` 10) для глубокого Dev-режима.

### 3.5. Безопасность и защита от вторжений (`security.py`)
- **`PSKAuthenticator` (Pre-Shared Key):**
  - Подпись HMAC-SHA256 с криптографической солью и одноразовым токеном nonce (`secrets.token_hex(16)`).
  - Сравнение хешей в постоянном времени через `hmac.compare_digest` — полная защита от тайминг-атак.
  - Защита от Replay-атак (повторного воспроизведения перехваченных пакетов): сервер держит кэш использованных nonce с ограничением по времени жизни.
  - Контроль рассинхронизации системных часов (`max_clock_skew_sec = 30s`).
- **Защита «кармана» от Path Traversal:**
  - Функция `validate_safe_path(base_dir, relative_path)` строго резолвит абсолютные пути.
  - Попытки передать имя файла вроде `../../etc/passwd` или `..\..\Windows\System32\cmd.exe` мгновенно пресекаются исключением `SecurityError`.
